**Data files are now written with zstd rather than Snappy.** No action is required and
nothing is rewritten — Parquet records the codec per column chunk, so existing files stay
readable untouched beside new ones, and a table holding both reads correctly through `scan`
and `sql`.

No write path had ever specified a codec at all: a seal, a compaction, an archive rewrite and
the new bulk ingest all called `pq.write_table` bare, taking pyarrow's Snappy default by
accident rather than by decision. It was found on a real 177M-row archive sitting at 34.83 GB
— 197 bytes/row against 81 in the legacy source it was loaded from, on a JSON payload column,
which is the shape zstd crushes and Snappy does not.

Measured end to end through `ingest` on a 400k-row JSON payload column: 28.5 MB against
15.2 MB, 71 bytes/row against 38. The default changed rather than the docs gaining advice
because it is not a size-for-speed trade — a full-scan read measured 0.65x Snappy's, since
there is less to read and decompressing it is cheap, and the load itself ran no slower. The
cost is write CPU, against a write path that is fsync-bound and an archive push that is
network-bound.

Set `LogConfig(compression=...)` to choose — `none`, `snappy`, `gzip` or `zstd`. It is a
setting rather than a constant because the right answer is a property of the payload: SPEC
§15.5 requires `none` for blob columns, where a codec spends CPU proving that
already-compressed bytes are incompressible. `rewrite_archive` re-cuts existing history into
the current codec, as a separate decision from adopting it.

Every sizing decision — compaction runs, what `sync` may push, what eviction may drop — reads
the appender's *uncompressed* byte count and never bytes on disk, so changing the codec cannot
move any of them on an existing log.

**`WriteHandle.ingest` loads Arrow without going through the SQLite buffer.**

```python
lo, hi = log.ingest(table)                              # a pa.Table
lo, hi = log.ingest(pq.ParquetFile(path).iter_batches())  # or a RecordBatchReader
```

The buffer exists to make a row durable before it is in Parquet, and a bulk load's source is
already durable — so every row pushed through it at `synchronous=FULL` pays a second time for
a guarantee it has. Measured on 400k rows on local disk, where fsync is cheap and the gap is
therefore understated: 182,801 rows/s through the buffer against 5,103,266 rows/s writing
straight out. Files come out sorted and sized at `target_compact_size`, so maintenance never
has to touch them.

It refuses concurrency rather than surviving it — the whole log is claimed for the whole load,
and every acknowledged row must already be in a file, so call `seal()` and `await_seal()`
first. It also refuses `wal_replication`, because these rows never enter the buffer and WAL
shipping therefore cannot carry them at all. **The archive is a loaded range's only second
copy: compare `archived_through()` against the `hi` that `ingest` returns.** Until they meet,
the corpus you loaded from is the range's second copy.

Bulk-loading history into a `start_offset` reserve *under live capture* is not this and
remains deferred.
