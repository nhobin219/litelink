**`ingest` now pushes its own output to the archive.** This is the entry to read if you bulk
load: it is a behaviour change, and it closes a real exposure rather than tidying one.

A loaded range never enters the SQLite buffer, so WAL replication cannot carry it — the archive
is its only second copy. But an ordinary `sync` held a load's short last file back, because
`stable_prefix` keeps a trailing run under the compaction budget on the reasoning that a run
with room in it may still take files nobody has written. On a stream that then goes quiet, the
run never settles and the file never ships. 0.2.2 documented that and told you to compare
`archived_through()` against the range `ingest` returned. Documenting it was not enough:
measured on a live deployment, **113,399 loaded rows sat on one disk** across nine streams,
with `coverage()` reporting no gap.

`ingest` now compacts and then pushes with `sync(push_unsettled=True)` when an archive is
configured. Pass `sync=False` to opt out. The push is a prefix, because the watermark it
records has to stay contiguous for eviction to trust it — which is why the compaction runs
first, so only what a run genuinely cannot fill reaches the archive. A push that fails leaves
the load durable and raises saying so, because retrying the load would reserve a fresh range
and duplicate it.

If you call `ingest` on a log with an archive configured, it now does network I/O where it
previously did not.

---

**A log whose buffer holds all of it can be followed.** `follow` refused any archive with no
published metadata pointer — which is exactly a slow capture: nothing reaches
`target_seal_size`, nothing is pushed, and with `wal_replication` a seal retains its rows, so
the buffer holds the whole log and the WAL carries every row there is. It was the one case
where a follower is the only way to read a log off-box, and the one case that did not work.

A follower now serves the buffer alone when it can prove the buffer *is* the log, which takes
two independent facts because rows go missing two ways: rows that left (a seal discarding, or
`release_archived`) raise the buffer's first offset, and rows that never entered (`ingest`
writes straight to Parquet) leave a hole inside the buffered range. The second is why `ingest`
records `ingested_through` at reservation time, before the file exists, where no later crash or
compaction can lose it.

---

**`reclaim_buffer()` and `vacuum_free_ratio`, for the dead space SQLite never returns.** Pages
freed by a delete go on a free list and the file never shrinks, so a buffer that seals and
archives for months keeps every page it ever needed. That is invisible locally — the free list
gets reused — and it is the *readers* who pay, because litestream replicates the file. Measured
on a one-day-old capture: 457 MB holding 20,658 live rows, 92% of its pages free, restoring in
12.5 s against 0.8 s for the same content vacuumed.

Off by default and manual, because the cost lands on the write path: `VACUUM` takes an
exclusive lock and rebuilds the file, so appends stall for as long as the live data takes to
copy. Only your deployment knows whether its arrival rate can absorb that.

---

**Smaller fixes.** A mistyped archive prefix is now refused where it is typed, instead of
surfacing as a YAML parse error out of the litestream subprocess. "There is no replica here"
reaches the caller again — both `restore` and `follow` carried that message and neither could
ever raise it. And `just rustfs` creates its bucket again, which had been silently skipping ~91
tests on a fresh checkout.
