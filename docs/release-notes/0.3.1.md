**A maintenance release: one round trip off an archive-only snapshot, and documentation that
was missing a directory.**

Assembling `snapshot(..., include_wal=False)` fetched `version-hint.text` three times and
parsed `metadata.json` twice for one assembly — `archive_shape` and `archive_extent` do the
identical first two steps, and the path called both. It is two fetches and one parse now.
Against a local endpoint that is noise; against a bucket at 60–75 ms RTT it is a round trip plus
a redundant `metadata.json` transfer, and on an archive with thousands of files that file is not
small.

Worth stating alongside it, because the question that found this was "why is an archive-only
snapshot slower than a raw `iceberg_scan`": it is not slower per query. Measured on a 200k-row
archive, a bounded scan through an open snapshot is **0.02 s** against **0.40 s** for a fresh
DuckDB connection, because the connection and the loaded extensions are reused and the
predicate still pushes down. What a one-shot script pays is the assembly, and it reuses none of
it — so for a single query in a script, the raw query really is the better tool. The README now
says so.

---

**`data/ingested/` is in the layout documentation.** Bulk ingest has written there since 0.2.2,
and neither the README's tree nor SPEC §2 mentioned it, so the only way to find out the
directory existed was to list the bucket. Both now show it beside `compacted/`, and SPEC names
the pass that writes each — including that `compacted/` holds `rewrite_archive`'s re-cuts as
well as compaction's output.

Nothing in this release changes an API or a format. Upgrading from 0.3.0 requires nothing.
